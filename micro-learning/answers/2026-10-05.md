## 3. workflow, agent, skill 区别
**English:**
The core difference comes down to who decides the next step. A workflow is a predefined, fixed pipeline — you write the code, and the model only fills in specific steps like classification or extraction, so it's deterministic and cheap. An agent is a dynamic loop where the model itself decides which tools to call and in what order, stopping only when it judges the task done; it's more flexible but harder to debug and more expensive. A skill is a reusable playbook — a prompt plus optionally scripts and reference docs — that teaches an agent how to do one specific task well, like using the Gmail API or booking a flight. So skills plug into agents, and you often combine all three: workflows for the predictable parts, agents for the open-ended parts, and skills to make the agent good at its tools.
**中文要点：**
- workflow：固定流程，代码决定步骤，LLM 只做局部填充，确定性强、便宜
- agent：LLM 自主决定调用哪些工具、什么顺序，灵活但难调试、贵
- skill：可复用的技能包（prompt + 脚本 + 文档），让 agent 更擅长某类任务
- 三者可以组合：确定性部分用 workflow，开放部分用 agent，skill 增强 agent 的工具能力

## 4. 如何提升 agent 的 function call 的能力
**English:**
Improving function calling comes down to three things: the model, the tool definitions, and the loop around them. First, pick a model that's actually good at tool use — benchmarks and real tests matter more than parameter count. Second, write tool schemas like API docs for a careful junior engineer: clear names, precise descriptions, required vs optional fields, concrete examples in the description, and keep the total number of tools small and non-overlapping so the model doesn't get confused. Third, strengthen the execution loop: add a ReAct-style "reason then act" prompt, validate arguments and return clear error messages so the model can self-correct, cap the max steps, and log every call so you can see where it goes wrong. In practice, most failures I see come from vague tool descriptions or too many similar tools, not from the model itself.
**中文要点：**
- 选模型：选 tool use 能力强的模型，看 benchmark 和实测而非参数量
- 写好工具定义：名字清晰、描述精确、区分必填/选填、description 里给例子，工具数量少且互不重叠
- 加强执行循环：ReAct 式先思考再行动、校验参数并返回清晰错误以便自纠正、限制最大步数
- 记录每步调用日志，多数失败源于工具描述模糊或工具过多相似，而非模型本身

## 5. agent 工具调用这方面，了解哪些方式
**English:**
There are several common ways an agent can call tools. The most standard is native function calling, where the model outputs structured JSON against a schema you define, and your code executes it. Then there's MCP — the Model Context Protocol — which standardizes how tools are exposed over a client-server connection, so any MCP client can discover and call tools from any MCP server without custom integration code. There's also the CodeAct or code-execution style, where instead of calling a named function the agent writes and runs code, like Python in a sandbox, which is more expressive for data tasks. Older or simpler setups use ReAct-style text parsing, where the model emits something like "Action: search, Input: ..." and you regex it out. And finally, skills bundle a prompt with helper scripts so the agent follows a proven procedure rather than improvising each call.
**中文要点：**
- Native function calling：模型输出结构化 JSON，代码按 schema 执行，最标准
- MCP：客户端-服务器协议，统一工具的发现与调用，免去定制集成
- CodeAct / 代码执行：agent 写代码并在沙箱运行，适合数据类任务，更灵活
- ReAct 文本解析：模型输出 "Action: ... Input: ..." 文本，正则提取，老式但简单
- Skill：prompt + 辅助脚本打包，让 agent 按既定流程调用而非临场发挥

## 6. 怎么保障 agent 按需调用工具
**English:**
Making an agent call tools only when needed is really about giving it good judgment and good guardrails. On the judgment side, the system prompt should spell out when each tool is appropriate and, just as importantly, when it isn't — for example, "only call the database tool when the user asks about their own data." On the guardrail side, you add structure: required confirmation for expensive or irreversible actions, a max-steps budget so it can't loop forever, and argument validation that rejects bad calls with an error message the model can learn from. I also like adding a lightweight planning step where the model first lists which tools it intends to use before executing, which cuts down on random exploratory calls. And of course, log everything — if you review the traces, the unnecessary calls usually reveal a vague tool description or a missing instruction.
**中文要点：**
- 系统 prompt 明确每个工具的适用场景和不适用场景，给出判断标准
- 护栏：高风险/不可逆操作要求确认、限制最大步数防止死循环、参数校验并返回可学习的错误信息
- 先规划后执行：让模型先列出打算用的工具，减少随意试探性调用
- 全量日志 + 复盘 trace，不必要的调用通常暴露工具描述模糊或指令缺失

## 7. function call、mcp、skill 的区别？
**English:**
These three sit at different layers. Function calling is the mechanism — the model decides to invoke a tool and emits structured arguments, and your code runs it. It's the "how" of a single call. MCP is the protocol — it standardizes how tools are served and discovered over a client-server connection, so instead of hand-writing integration code for every tool, any MCP-compatible client can talk to any MCP server. It's the "how tools get plugged in at scale." A skill is the knowledge layer — a reusable package of prompt, scripts, and docs that teaches the agent the right procedure for a task, like "how to triage a Gmail inbox." So roughly: function calling is the verb, MCP is the interface standard, and skills are the know-how that makes the calls actually good.
**中文要点：**
- function call：调用机制，模型决定调用并输出结构化参数，代码执行——单次调用的"怎么做"
- MCP：协议层，标准化工具的服务与发现，客户端-服务器架构——规模化接入的"怎么插进来"
- skill：知识层，可复用的 prompt + 脚本 + 文档，教 agent 正确的做事流程——让调用真正有效的" know-how"
- 一句话：function call 是动词，MCP 是接口标准，skill 是经验

## 8. skills 和 rules 的区别？
**English:**
Rules and skills both guide the model's behavior, but they differ in scope and timing. Rules are short, always-on constraints or preferences loaded into every conversation — things like "always respond in Chinese" or "never use emojis." They're cheap, global, and best for style and hard boundaries. Skills are task-scoped playbooks that get loaded only when relevant — they contain detailed instructions, examples, and sometimes scripts for doing one specific thing well, like "how to write a migration" or "how to use the Stripe API." A good mental model: rules are the employee handbook that applies to everyone every day, while a skill is the training manual you pull out when you're assigned a specific job. In practice you keep rules few and stable, and grow a library of skills for specialized tasks.
**中文要点：**
- rules：短小、常驻的全局约束/偏好（如"默认中文回复"），每次都加载，管风格和硬边界
- skills：任务级 playbook，只在相关时加载，含详细指令、示例甚至脚本，管"把某件事做好"
- 心智模型：rules 是员工手册（人人每天遵守），skill 是专项培训手册（接到具体任务才翻）
- 实践：rules 少而稳定，skills 按需增长成库

## 9. MCP 的使用场景
**English:**
MCP shines whenever you want tools to be reusable across different agents and apps instead of writing one-off integrations. The classic use case is giving an agent access to external data and services — a Postgres MCP server lets any MCP client query your database, a filesystem server gives sandboxed file access, a GitHub server enables repo operations. It's also great for enterprise settings where IT wants one governed, audited way to expose internal APIs to AI tools rather than every team building custom connectors. Another growing use case is desktop and IDE assistants — tools like Claude Code use MCP so users can plug in their own data sources with a config file instead of code. Basically, if more than one agent needs the same tool, or you want third parties to extend your product, MCP is worth it; for a single throwaway script, direct function calling is simpler.
**中文要点：**
- 跨 agent/app 复用工具：Postgres、文件系统、GitHub 等 MCP server，一次接入多处可用
- 企业内控：IT 统一暴露内部 API 给 AI 工具，可审计、可治理，避免各团队重复造轮子
- 桌面/IDE 助手：配个 config 就能接入自己的数据源，无需写代码
- 判断标准：多个 agent 共用同一工具、或想让第三方扩展 → 用 MCP；一次性脚本 → 直接 function call 更简单

## 10. 如何理解 Agent 中的长短期记忆？实际项目中分别如何实现？
**English:**
Short-term memory is the conversation context — what the agent remembers within the current session. It's implemented with the context window itself, plus practical tricks like sliding-window truncation, summarization of older turns, and keeping a scratchpad of intermediate reasoning. Long-term memory is what persists across sessions: user preferences, facts, past decisions. In real projects that's usually a vector database or a structured store — you embed conversation chunks or extracted facts, retrieve the relevant ones at the start of a new session, and inject them into the prompt. A common pattern is a nightly or on-write job that extracts durable facts from conversations and upserts them into the memory store, with timestamps and confidence scores. The key design decisions are what to remember, how to retrieve it with good precision, and how to let old or wrong memories expire or be corrected.
**中文要点：**
- 短期记忆 = 当前会话上下文：context window + 滑动窗口截断、历史摘要、scratchpad
- 长期记忆 = 跨会话持久化：用户偏好、事实、过往决策
- 实现：向量库/结构化存储存 embedding 后的对话片段或抽取的事实，新会话开始时检索注入 prompt
- 常用模式：定时或写入时从对话抽取持久事实，upsert 进记忆库，带时间戳和置信度
- 关键设计：记住什么、精准检索、过期/纠错机制

## 11. prompt 你会怎么考量去写
**English:**
When I write a prompt, I think about four things: role, task, constraints, and examples. First, give the model a clear role and context so it knows what it's doing and who it's serving. Second, state the task as a concrete, verifiable goal — "summarize in three bullet points" beats "summarize well." Third, spell out constraints explicitly: format, length, tone, what to do when information is missing, and what never to do — models don't reliably infer your unspoken rules. Fourth, include one or two few-shot examples for anything where the output shape matters; examples teach format far better than paragraphs of description. Then I iterate: run it against real inputs, look at failures, and tighten the prompt where it actually went wrong rather than adding defensive instructions for imagined problems. And keep it maintainable — prompts are code, so version them and test changes like you would any code change.
**中文要点：**
- 四要素：角色（role+上下文）、任务（具体可验证的目标）、约束（格式/长度/缺信息时怎么办/禁区）、示例（few-shot）
- 任务描述要具体可验证，"三条 bullet 总结"胜过"好好总结"
- 约束要显式写出，模型不会可靠推断你的潜规则
- 输出格式重要的地方用 1-2 个例子，例子比大段描述更有效
- 迭代：用真实输入跑，看失败 case 再收紧；prompt 也是代码，要版本管理和测试

## 12. 记忆覆盖问题如何解决
**English:**
Memory overwrite happens when new information clobbers still-useful old memories — for example, the agent learns a user's new address and loses the old context it actually needed. The fix starts with never doing blind upserts: store memories as versioned records with timestamps instead of mutating a single value. Then add a merge policy — when new info arrives, decide whether it replaces, supplements, or conflicts with the old one; conflicts should be flagged rather than silently overwritten. In retrieval, prefer recency-weighted ranking but keep older memories reachable, and show the agent the timestamp so it can reason about which is current. Finally, keep a human-in-the-loop escape hatch: let users view and correct their stored memories, because no automatic policy gets every merge right.
**中文要点：**
- 根因：盲目 upsert，新信息直接覆盖仍有用的旧记忆
- 版本化存储：记忆带时间戳的多版本记录，而非原地修改单个值
- 合并策略：新信息到来时判断是替换/补充/冲突，冲突要标记而非静默覆盖
- 检索侧：按时间加权排序但保留旧记忆可达，把时间戳给模型让它自己判断哪个最新
- 兜底：允许用户查看和纠正记忆，自动策略不可能每次都合并正确

## 13. Agentic RAG 和传统 RAG 的区别
**English:**
Traditional RAG is a fixed pipeline: retrieve once, then generate. You embed the query, pull the top-k chunks, stuff them into the prompt, and the model answers in one shot. It works fine for simple factual questions but breaks down when the question needs multiple hops or the first retrieval misses. Agentic RAG turns the model into an active researcher: it can decide to search, read the results, realize it needs more, reformulate the query, call other tools like a calculator or a database, and iterate until it has enough to answer. The trade-off is the usual one — agentic RAG handles complex, multi-step questions much better, but it's slower, more expensive, and harder to evaluate because the path isn't deterministic. In practice I use traditional RAG for straightforward Q&A and reach for agentic RAG when questions need reasoning over multiple sources.
**中文要点：**
- 传统 RAG：固定 pipeline，检索一次 → 生成一次，适合简单事实问答
- Agentic RAG：模型主动研究，可多次检索、改写 query、调用其他工具，迭代直到信息足够
- 传统 RAG 在多跳问题或首次检索失败时容易崩
- 代价：agentic 更慢、更贵、路径不确定难评估；简单问答用传统，多源推理用 agentic

## 14. 你了解 RAG 的分片逻辑吗？
**English:**
Chunking is about splitting documents into pieces that are small enough to fit retrieval and the context window, but big enough to stay meaningful on their own. The simplest approach is fixed-size chunking — say 512 tokens with some overlap — which is easy but can cut sentences and ideas in half. Better approaches respect document structure: split by paragraphs, sections, or markdown headers first, then subdivide anything still too long. Semantic chunking goes further and splits where the topic shifts, using embedding similarity between sentences. And the overlap — typically 10 to 20 percent — exists so that a key sentence sitting on a boundary isn't lost; both neighboring chunks carry it. The right choice depends on the documents: clean structured docs do well with recursive or header-based splitting, while messy text benefits from semantic chunking.
**中文要点：**
- 目标：块要小到能检索、能进上下文，又大到自身语义完整
- 固定大小切分（如 512 tokens）：简单但会切断句子和语义
- 结构化切分：先按段落/章节/markdown 标题切，过长的再细分
- 语义切分：按 embedding 相似度在话题切换处切分，适合杂乱文本
- overlap（通常 10-20%）：让边界上的关键句子同时落在相邻两块，避免丢失

## 15. 召回时分片不完整怎么办？
**English:**
Incomplete chunks at retrieval time usually mean the answer got split across chunk boundaries, so the fix is to give the model more surrounding context. The most direct approach is surrounding-context expansion: when a chunk is retrieved, also pull its neighbors — the chunks before and after it in the original document — and feed all of them to the model. A related technique is parent-document retrieval, where you search over small chunks for precision but return the larger parent section for generation. You can also use sentence-window retrieval: index individual sentences for fine-grained matching, then expand to a window of surrounding sentences at read time. And of course, increasing overlap at chunking time reduces the problem upstream. If the issue persists, it's often a sign the chunks are too small or the split points are bad, and re-chunking is the real fix.
**中文要点：**
- 上下文扩展：召回某块时同时取其前后相邻块，一起喂给模型
- Parent-document retrieval：用小块做精准检索，返回其所属的大段落用于生成
- Sentence-window：按单句建索引，读取时扩展为前后句子窗口
- 上游缓解：切分时加大 overlap
- 持续出现说明块太小或切分点差，根本解法是重新切分

## 16. 如何选择合适的切块大小和重叠长度？
**English:**
There's no universal answer — chunk size is a trade-off between retrieval precision and context completeness, so I always tune it empirically. Smaller chunks, like 200 to 300 tokens, give more precise retrieval because each chunk is focused, but they risk losing the surrounding context the model needs to answer. Larger chunks, like 800 to 1000 tokens, preserve context but dilute the embedding and eat the context window faster. My practical approach: start around 512 tokens with 10 to 20 percent overlap, build a small evaluation set of real questions with known answers, and measure retrieval hit rate and end-to-end answer quality while varying the size. Also match the chunk to the document type — Q&A pairs or FAQ entries can be one chunk each, while long reports need structural splitting. And remember the model's context window sets a hard ceiling on how many chunks you can include.
**中文要点：**
- 本质 trade-off：小块检索精准但易丢上下文，大块保上下文但 embedding 被稀释、占上下文窗口
- 实操：从 512 tokens + 10-20% overlap 起步，用真实问题的小评估集测召回命中率和端到端质量，再调参
- 按文档类型匹配：FAQ 一问一答可一块一条，长报告用结构化切分
- 上限约束：模型的 context window 决定了能塞进多少块

## 17. 哪些可以提升 RAG 检索质量的技术？
**English:**
Retrieval quality can be improved at every stage of the pipeline. Before retrieval, rewrite or expand the query — HyDE generates a hypothetical answer and searches with it, and query expansion adds synonyms or sub-questions. During retrieval, hybrid search combining dense vectors with BM25 keyword matching catches both semantic and exact-term matches, and you can search at multiple granularities. After retrieval, reranking with a cross-encoder model reorders the candidates much more accurately than bi-encoder similarity alone. You can also improve the index itself: better chunking, adding metadata filters, and periodically refreshing embeddings. And at generation time, techniques like parent-document retrieval or context compression keep the prompt focused. If I had to pick the highest-ROI moves, they'd be hybrid search plus a reranker — those two alone fix most mediocre RAG systems.
**中文要点：**
- 检索前：query 改写/扩展，HyDE 用假设答案去搜，加同义词或子问题
- 检索中：hybrid search（稠密向量 + BM25），兼顾语义和精确词匹配；多粒度检索
- 检索后：cross-encoder reranker 重排，比双塔相似度准得多
- 索引侧：更好的切分、metadata 过滤、定期更新 embedding
- 生成侧：parent-document retrieval、上下文压缩
- ROI 最高的两个：hybrid search + reranker

## 18. SSE 是如何实现边生成边推送的？
**English:**
SSE, or Server-Sent Events, is a simple HTTP-based protocol where the server keeps one long-lived connection open and pushes text events to the client as they happen. For streaming LLM output, the flow is: the client sends the prompt with a normal request, the server sets the response headers to `Content-Type: text/event-stream` and disables buffering, then as the model generates each token, the server immediately writes it as an SSE `data:` event and flushes it down the open connection. The browser's EventSource API or a fetch reader consumes these events and appends the text to the UI in real time. It's one-directional — server to client only — which is all you need for generation streaming, and it's simpler than WebSockets because it's just HTTP with no handshake upgrade. The main gotchas are proxies that buffer responses and clients that need reconnection logic if the connection drops.
**中文要点：**
- SSE = 基于 HTTP 的单向长连接，服务器持续向客户端推送文本事件
- 流程：客户端发请求 → 服务端返回 `Content-Type: text/event-stream` 并关闭缓冲 → 每生成一个 token 立刻写成 `data:` 事件 flush 出去
- 客户端用 EventSource 或 fetch reader 实时消费、逐字拼到 UI
- 单向（server→client），生成流场景够用；比 WebSocket 简单，就是普通 HTTP 无需升级握手
- 坑：中间代理可能缓冲响应、断线需要客户端重连逻辑

## 19. redis 的 hash 大 key 怎么优化？
**English:**
A big hash key in Redis is a problem because commands like HGETALL block while serializing a huge object, and a single hot key can't be sharded across a cluster. The standard fix is to split it: instead of one hash with millions of fields, shard it into many smaller hashes using a suffix on the key name, like `user:1234` instead of one `users` hash — the application hashes the field to pick the shard. Keep each shard small enough that operations stay fast, typically thousands to low tens of thousands of fields. Also avoid HGETALL and KEYS on big hashes entirely; use HSCAN for iteration and fetch only the fields you need. If the hash holds data with different access patterns or TTLs, that's another reason to split it by usage. And monitor with `MEMORY USAGE` or `--bigkeys` so you catch new big keys before they become incidents.
**中文要点：**
- 问题：HGETALL 等命令序列化大对象会阻塞；单个 key 无法在集群间分片
- 标准解法：拆分——按字段 hash 取模打散成多个小 hash（如 `user:1234`），应用层决定路由
- 每个分片控制在几千到几万 field，保证操作快速
- 禁用 HGETALL/KEYS，用 HSCAN 迭代、只取需要的 field
- 不同访问模式/TTL 的数据按用途拆分；用 `MEMORY USAGE` / `--bigkeys` 监控，早发现

## 20. 手撕——快排
**English:**
QuickSort is a divide-and-conquer sort: pick a pivot element, partition the array so everything smaller goes left and everything larger goes right, then recursively sort the two sides. The key insight for interviews is the partition step — the classic Lomuto or Hoare scheme does it in place with two pointers in O(n) time. Average time complexity is O(n log n) because each level splits the array roughly in half, but the worst case is O(n²) when the pivot is always the min or max, which happens with already-sorted input and a naive pivot choice. That's why production implementations use tricks like median-of-three pivot selection or random pivots, and switch to insertion sort for tiny subarrays. Space is O(log n) for the recursion stack on average. It's not stable, but it's cache-friendly and fast in practice, which is why it's the default in most standard libraries.
**中文要点：**
- 思想：分治，选 pivot → partition（小的放左、大的放右）→ 递归排两侧
- partition 是关键：Lomuto/Hoare 双指针原地划分，O(n)
- 平均 O(n log n)，最坏 O(n²)（pivot 总选到最大/最小，如有序数组 + 固定取首元素）
- 工程优化：三数取中/随机 pivot 防最坏，小数组切插入排序
- 空间 O(log n)（递归栈），不稳定，但 cache 友好、实际快，是多数标准库默认排序

## 1. Agent 系统中的 LangGraph 是如何搭建的？其 Memory 组件的工作机制是怎样的？

**English:**
LangGraph lets you build agents as graphs where each node is a step—an LLM call, a tool, or a subagent—and edges define the transitions. For a typical agent I create nodes for planning, tool execution, and synthesis, then add conditional edges so the graph can loop back to the planner when more work is needed. For memory, LangGraph provides a checkpointer that saves the graph state after every node runs, and a MemorySaver persists thread-level state like chat history. There are also longer-term stores: a cross-thread store for facts about the user, with semantic search to retrieve relevant memories. I usually combine the checkpointer for short-term working state with a vector store for long-term memory keyed by user or session.

**中文要点：**
- LangGraph 把 Agent 建模成图：节点是 LLM 调用、工具或子 Agent，边决定流转，条件边支持循环
- 典型搭建：规划节点 → 工具执行节点 → 综合节点，用条件边回环继续规划
- Memory 组件：checkpointer 每节点执行后保存图状态，线程级保存对话历史
- 长时记忆：跨线程的 store 存用户信息，配合语义检索召回相关记忆
- 实践组合：checkpointer 做短期工作状态 + 向量库做长期记忆

## 2. 你为什么要拆子 Agent？

**English:**
I split work into subagents for three main reasons. First, isolation: each subagent gets its own context window, so a deep research task doesn't pollute the main agent's context with irrelevant details. Second, specialization: a subagent can carry a focused system prompt and a narrow tool set, which makes its behavior more reliable and easier to test. Third, parallelism: independent subtasks can run concurrently, which speeds things up. The trade-off is orchestration overhead—the parent agent has to define clear interfaces and consolidate results, so I only split when the task genuinely benefits from isolation or parallel execution.

**中文要点：**
- 隔离上下文：子 Agent 有独立上下文窗口，避免细节污染主 Agent 的上下文
- 专业化：聚焦的系统提示词和精简工具集，行为更可靠、更易测试
- 并行执行：独立子任务并发运行，提升整体速度
- 代价：编排开销，父 Agent 要定义清晰接口并汇总结果；只有真正需要隔离或并行时才拆

## 3. 你觉得多 Agent 在什么情况下容易出错？

**English:**
Multi-agent setups fail most often when the contract between agents is vague. If a subagent returns a free-form summary instead of a structured result, the parent agent has to guess what it meant, and errors compound. Another classic failure is infinite delegation loops—one agent keeps bouncing a task to another without progress, so I always set depth limits and pass-through budgets. Shared mutable state is also risky: two agents writing to the same file or database can clobber each other's work. Finally, context drift: agents that only see summaries of summaries lose grounding in the original task, so I make sure each agent receives the original goal and verifiable inputs, not just paraphrased instructions.

**中文要点：**
- Agent 之间契约模糊：返回自由文本而非结构化结果，误差逐层放大
- 无限委派循环：任务被来回踢皮球，要设深度限制和预算上限
- 共享可变状态：多 Agent 写同一文件/数据库会互相覆盖
- 上下文漂移：只看到"摘要的摘要"的 Agent 会偏离原始目标，要给每个 Agent 原始目标和可验证输入

## 4. skill 和多 Agent 执行的区别

**English:**
A skill is a packaged, deterministic capability—a documented playbook plus its tools and guardrails that any agent can invoke, like sending email or querying a database. Multi-agent execution is an orchestration pattern: several autonomous agents collaborate, each with its own goal, context, and decision loop. The key difference is agency: a skill doesn't decide what to do, it just executes a well-defined procedure, while agents make their own plans. I use skills for repeatable, low-variance tasks where I want consistency, and multiple agents when the task needs diverse expertise or genuinely parallel exploration where the decomposition itself requires judgment.

**中文要点：**
- skill 是封装好的确定性能力包：文档化流程 + 工具 + 护栏，被 Agent 调用
- 多 Agent 执行是编排模式：多个自主 Agent 各带目标、上下文和决策循环协作
- 核心区别是自主性：skill 只执行定义好的流程，不做决策；Agent 会自己规划
- 用 skill 做可重复、低方差的任务求一致性；用多 Agent 做需要多样专长或分解本身就需要判断的任务

## 5. agent 结构化输出信息是啥？

**English:**
Structured output means forcing the LLM to return data in a predefined schema—like JSON matching a Pydantic model—instead of free text. I use it whenever the agent's result feeds into downstream code: tool arguments, database writes, or handoffs between agents. The model gets the schema in its prompt and the output is validated; if validation fails, the framework retries with the error message. This kills an entire class of parsing bugs and lets the parent agent trust the shape of what comes back. The trade-off is slightly lower flexibility, but for machine-consumed outputs it's almost always worth it.

**中文要点：**
- 结构化输出：强制 LLM 返回预定义 schema（如 JSON/Pydantic 模型）而非自由文本
- 用在结果要被下游消费的场景：工具参数、写库、Agent 间交接
- 机制：schema 进提示词，输出做校验，校验失败带错误信息重试
- 好处：消除整类解析 bug，父 Agent 可以信任返回的数据结构

## 6. skill 和 memory 的沉淀怎么设计？

**English:**
I treat skills and memory as two different kinds of accumulation. Skills are codified procedures: when I find myself repeating the same multi-step workflow, I extract it into a skill with a clear name, input-output contract, and embedded guardrails, then version it so improvements don't break existing callers. Memory is accumulated experience: per-user preferences, past decisions, and lessons learned, stored with timestamps and provenance so stale facts can be pruned. The design principle is that skills capture "how to do things" and memory captures "what we know"; a promotion pipeline moves repeated observations from memory into candidate skills when a pattern stabilizes.

**中文要点：**
- skill 沉淀的是"怎么做"：重复出现的多步流程抽象成 skill，带清晰输入输出契约和护栏，做版本管理
- memory 沉淀的是"知道什么"：用户偏好、历史决策、经验教训，带时间戳和来源，过期可清理
- 设计原则：skill 捕获流程，memory 捕获知识
- 晋升通道：memory 里反复出现的稳定模式，可以提炼成候选 skill

## 7. 动态 workflow 了解吗？

**English:**
Yes. A dynamic workflow is one where the execution plan isn't fixed upfront—the agent decides the next step at runtime based on intermediate results. LangGraph's conditional edges are a simple form of this: the graph branches based on what the last node produced. More advanced versions use a planner agent that generates or revises the DAG on the fly, adding or skipping steps as new information arrives. The advantage is adaptability to unpredictable tasks; the risk is nondeterminism, which makes testing harder. In practice I mix static scaffolding for the critical path with dynamic branching for the exploratory parts, and I cap loops with explicit termination conditions.

**中文要点：**
- 动态 workflow：执行计划不是预先固定，Agent 根据中间结果在运行时决定下一步
- 简单形式：LangGraph 的条件边，根据上一步产出分支
- 高级形式：规划 Agent 动态生成/修订 DAG，随新信息增删步骤
- 优势是适应不可预测任务，风险是非确定性导致难测试
- 实践：关键路径用静态骨架，探索部分用动态分支，并设显式终止条件

## 8. agent 开发流程有几个环节？

**English:**
I think of agent development in five stages. First, scoping: define the task, the success criteria, and what the agent is explicitly not allowed to do. Second, design: choose the architecture—single agent, ReAct loop, or multi-agent—and define tools, memory, and guardrails. Third, implementation: build the prompts, tool schemas, and orchestration logic, usually starting from the simplest version that could work. Fourth, evaluation: run it against a set of test cases including edge cases and adversarial inputs, and measure both task success and safety metrics. Fifth, deployment and iteration: ship with logging and human-in-the-loop checkpoints, then keep refining prompts and tools based on real failures.

**中文要点：**
- 范围界定：定义任务、成功标准和明确禁止事项
- 设计：选架构（单 Agent/ReAct/多 Agent），定义工具、记忆和护栏
- 实现：写提示词、工具 schema、编排逻辑，从最简可用版本开始
- 评估：用测试集（含边界和对抗输入）跑，衡量任务成功率和安全指标
- 部署迭代：带日志和人工检查点上线，根据真实失败持续优化

## 9. workflow 编排参考啥？偏确定还是偏自由？

**English:**
I design orchestration around the failure cost of the task. For high-stakes, repeatable processes—like payments or data migrations—I lean deterministic: explicit state machines or fixed pipelines with validation at each step, because I need auditability and predictable behavior. For open-ended research or creative tasks, I give the agent more freedom with a ReAct-style loop and loose guardrails. My default is a hybrid: a deterministic scaffold for the critical path with clear checkpoints, and freedom inside each step for the agent to choose tools and strategies. The reference I use is: the more irreversible the action, the more deterministic the orchestration should be.

**中文要点：**
- 编排依据任务的失败成本来定
- 高风险、可重复流程（支付、数据迁移）：偏确定，显式状态机 + 每步校验，要可审计
- 开放式研究/创意任务：偏自由，ReAct 循环 + 宽松护栏
- 默认混合：关键路径用确定性骨架 + 检查点，步骤内部给 Agent 自由选择工具和策略
- 原则：动作越不可逆，编排越要确定

## 10. 什么情况下用 ReAct，什么情况下用 Plan and Execute？

**English:**
I use ReAct when the task is exploratory and the next step depends heavily on what the last tool call returned—like debugging or web research, where you can't know the plan until you see the data. Its strength is adaptability, and its weakness is myopia: it can wander or get stuck in loops without a global view. I use Plan-and-Execute when the task decomposes cleanly into known subtasks with dependencies—like "gather data, analyze, write report"—because the upfront plan gives better global coherence and each executor can be simpler. A good rule of thumb: if you can sketch the steps before starting, use Plan-and-Execute; if the steps only reveal themselves as you go, use ReAct, and consider replanning when the executor deviates.

**中文要点：**
- ReAct：探索性任务，下一步强依赖上一步工具返回的结果（如调试、网络调研），数据没出来之前无法定计划
- ReAct 缺点：短视，容易漫游或陷入循环，缺全局视角
- Plan and Execute：任务能清晰分解为有依赖关系的子任务（如"收集数据→分析→写报告"），前置计划带来更好的全局一致性
- 经验法则：动手前能画出步骤就用 Plan and Execute；步骤只能边做边显现就用 ReAct，执行偏离时可重新规划

## 11. Agent 是怎么选择工具的

**English:**
Tool selection happens through the function-calling interface: the model sees each tool's name, description, and parameter schema, and decides which to invoke based on the current goal and conversation state. Good tool design matters enormously here—I write descriptions that say when to use the tool and when not to, because the model literally reads them to decide. For agents with many tools, I narrow the candidate set dynamically: only expose relevant tools per step, or use a router that pre-filters. After a tool returns, the agent reads the observation and picks the next tool, looping until the goal is met. When selection goes wrong, it's usually because two tools overlap or a description is ambiguous, so I treat tool descriptions as a first-class design surface.

**中文要点：**
- 通过 function calling：模型看到工具名、描述、参数 schema，结合当前目标和对话状态决定调用哪个
- 工具描述是关键设计面：写清楚何时用、何时不用，模型是靠读描述做决策的
- 工具多时动态收窄候选集：每步只暴露相关工具，或用 router 预过滤
- 循环机制：读工具返回的 observation 再选下一个，直到目标达成；选错多因工具功能重叠或描述含糊

## 12. RAG 系统整体流程，对于不同类型的文档分块策略

**English:**
A RAG pipeline has four stages: ingestion, indexing, retrieval, and generation. Documents are loaded, cleaned, and chunked; each chunk is embedded and stored in a vector index with metadata. At query time, the query is embedded, the top-k chunks are retrieved, and they're injected into the prompt for the generator to answer. Chunking strategy depends on document type: for prose like articles I use semantic or paragraph-aware chunks of a few hundred tokens with overlap; for code I chunk by function or class boundaries so chunks stay syntactically complete; for tables I keep rows together or convert to markdown with headers preserved; and for PDFs with mixed layout I extract by section headings. The principle is to keep each chunk semantically self-contained so retrieval returns coherent units.

**中文要点：**
- 整体流程：文档摄入（加载清洗）→ 索引（分块、向量化、存索引+元数据）→ 检索（query 向量化、召回 top-k）→ 生成（chunk 注入 prompt 作答）
- 散文/文章：语义或段落感知分块，几百 token，带 overlap
- 代码：按函数/类边界分块，保持语法完整
- 表格：整行保留或转 markdown 保留表头
- 混合排版 PDF：按章节标题提取
- 原则：每个 chunk 语义自包含，检索返回连贯单元

## 13. 检索是怎么做的，生成怎么控制幻觉

**English:**
Retrieval usually combines dense vector search with sparse keyword search like BM25, then fuses the rankings—hybrid search catches both semantic matches and exact terms. I add a reranking step with a cross-encoder on the top candidates, plus metadata filters to scope by source or date. For hallucination control, the generator is instructed to answer only from the provided context and to say "I don't know" when the context is insufficient. I also use citations: the model must quote or reference the source chunk for each claim, which makes answers verifiable. Post-generation, I can run a faithfulness check comparing claims against retrieved passages, and lower the temperature to keep the model from improvising.

**中文要点：**
- 检索：稠密向量检索 + BM25 等稀疏检索做混合，排序融合；top 候选再用 cross-encoder 重排，加元数据过滤限定范围
- 幻觉控制：指示模型只基于给定上下文回答，上下文不足时说不知道
- 引用机制：每个论断必须引用来源 chunk，答案可验证
- 生成后可做忠实度校验（论断 vs 检索段落比对），并调低 temperature 减少即兴发挥

## 14. 还有没有其他的索引方式？

**English:**
Beyond flat vector indexes, there are several alternatives worth knowing. HNSW is the most common ANN algorithm—it builds a layered graph for fast approximate nearest-neighbor search and is what most vector databases use under the hood. IVF partitions vectors into clusters and only searches the nearest clusters, trading some recall for speed. For keyword-heavy needs, inverted indexes like BM25 remain strong and are cheap. Knowledge graphs index entities and their relationships, which helps multi-hop questions that pure similarity search misses. And newer approaches like ColBERT use late-interaction token-level embeddings for finer-grained matching. In practice I pick based on the query pattern: HNSW for general semantic search, BM25 or hybrid for exact terms, and graph-based indexing when relationships between facts matter.

**中文要点：**
- HNSW：最常用的 ANN 算法，分层图做近似最近邻搜索，主流向量库底层都用它
- IVF：把向量聚类分区，只搜最近的簇，用召回换速度
- 倒排索引（BM25）：关键词场景依然强且便宜
- 知识图谱：索引实体和关系，擅长多跳问题，纯相似度搜索做不好
- ColBERT 等 late-interaction：token 级嵌入做更细粒度匹配
- 选型看查询模式：通用语义搜 HNSW，精确词用 BM25/混合，事实间关系重要用图索引

## 15. 提示词攻击怎么防护

**English:**
Prompt injection defense works in layers. First, separate instructions from data: mark untrusted content clearly—with delimiters or metadata tags—so the model knows it's data, not commands. Second, least privilege: give the agent only the tools and permissions it needs, so even a successful injection can't do much damage. Third, input and output filtering: scan untrusted inputs for known injection patterns and validate the agent's planned actions before execution, especially irreversible ones. Fourth, use a smaller model or classifier as a guardrail to review suspicious content. No single layer is foolproof—injections are an arms race—so I combine structural separation, privilege limits, and human-in-the-loop review for high-stakes actions.

**中文要点：**
- 分层防御：指令与数据分离，用分隔符/元数据标记不可信内容，明确那是数据不是命令
- 最小权限：只给 Agent 必需的工具和权限，注入成功也造成有限损害
- 输入输出过滤：扫描已知注入模式，执行前校验 Agent 的计划动作，尤其不可逆操作
- 用小模型/分类器做护栏审查可疑内容
- 没有银弹，注入是攻防对抗：结构分离 + 权限限制 + 高风险动作人工复核组合使用

## 16. 怎样去设计一个 Agent 的沙箱机制

**English:**
A sandbox gives the agent a contained environment where mistakes can't escape. I design it in three layers. The execution layer runs code in an isolated container or VM with no network access by default, strict CPU/memory/time limits, and a read-only filesystem except for a scratch directory. The permission layer controls what the agent can touch: an allowlist of tools and APIs, rate limits, and confirmation gates before irreversible actions like sending emails or deleting data. The observation layer logs everything—commands, file changes, network attempts—so there's a full audit trail and anomalies can trigger a kill switch. The key design goal is that the blast radius of any single agent action is bounded and recoverable.

**中文要点：**
- 执行层隔离：容器/VM 跑代码，默认无网络，CPU/内存/时间设限，除临时目录外文件系统只读
- 权限层控制：工具和 API 白名单、限流，不可逆操作（发邮件、删数据）前加确认关卡
- 观测层记录：所有命令、文件变更、网络尝试记日志，形成审计链，异常触发熔断
- 设计目标：任何单个 Agent 动作的爆炸半径有界、可恢复

## 17. 使用 zset 进行限流的瓶颈在哪？

**English:**
The classic Redis-sorted-set rate limiter works by adding a timestamp-scored member per request and counting members inside a sliding window. Its bottleneck is write amplification: every request does a ZADD plus a ZREMRANGEBYSCORE cleanup, so at high QPS you're hammering Redis with writes, and each key's sorted set keeps growing between cleanups, costing memory. It also doesn't scale horizontally on its own—all instances must share one Redis, making Redis the single chokepoint and a single point of failure. Alternatives like the token-bucket algorithm need only one counter update per request, and fixed-window counters are even cheaper. I'd still use the zset approach when I need precise sliding-window semantics at moderate scale, but for very high throughput I'd move to token bucket or a dedicated rate-limiting service.

**中文要点：**
- 原理：每次请求 ZADD 一个带时间戳的成员，统计滑动窗口内成员数；瓶颈在写放大
- 每次请求至少一次 ZADD + 一次 ZREMRANGEBYSCORE 清理，高 QPS 下 Redis 写压力大
- 清理间隙 zset 持续膨胀，占内存
- 横向扩展受限：所有实例共享一个 Redis，Redis 成单点瓶颈和单点故障
- 替代：令牌桶每次请求只需一次计数器更新，开销更小；中等规模、需要精确滑动窗口语义时 zset 仍可用

## 18. 介绍一下 MVCC？

**English:**
MVCC, or Multi-Version Concurrency Control, lets databases handle concurrent reads and writes without heavy locking. Instead of blocking readers when a row is updated, the database keeps multiple versions of the row, each tagged with the transaction ID that created it. A transaction sees a consistent snapshot: it reads the newest version that was committed before its snapshot was taken, so readers never block writers and writers never block readers. Write-write conflicts are still resolved with locks—two transactions updating the same row will serialize. PostgreSQL implements this by storing old row versions in the same table and cleaning them up with vacuum, while InnoDB keeps undo logs to reconstruct older versions.

**中文要点：**
- MVCC（多版本并发控制）：用多版本代替重锁，实现读写并发
- 行更新时不阻塞读：保留行的多个版本，每个版本带创建它的事务 ID
- 事务看到一致性快照：读快照时刻之前已提交的最新版本，读写互不阻塞
- 写写冲突仍用锁解决：两个事务更新同一行会串行化
- 实现差异：PostgreSQL 把旧版本存在表里靠 vacuum 清理，InnoDB 用 undo log 重建旧版本

## 19. SSE 和 WebSocket 的区别？

**English:**
SSE, Server-Sent Events, is a one-way channel: the server pushes a stream of events to the client over a plain HTTP connection, and the client can't send data back through it. It's simple—built on HTTP, auto-reconnects, and works through most proxies—but limited to text and server-to-client flow, which makes it ideal for notifications, live feeds, or streaming LLM tokens. WebSocket is a full-duplex protocol: after an HTTP handshake it upgrades to a persistent bidirectional connection where either side can send text or binary frames anytime. That makes it the choice for chat, gaming, or collaborative editing where the client also needs to push data in real time. The trade-off is complexity: WebSockets need connection management, heartbeats, and more careful proxy configuration.

**中文要点：**
- SSE：单向，服务器经普通 HTTP 连接向客户端推送事件流，客户端不能回传；简单、自动重连、穿透代理好，只支持文本
- 适用 SSE：通知、实时 feed、流式输出 LLM token
- WebSocket：全双工，HTTP 握手后升级为持久双向连接，双方可随时收发文本/二进制帧
- 适用 WebSocket：聊天、游戏、协同编辑等客户端也要实时推送的场景
- 代价：WebSocket 需要连接管理、心跳、更复杂的代理配置

## 20. 最后一个是旋转数组搜索

**English:**
Searching in a rotated sorted array is a classic modified binary search. The key insight is that at any midpoint, at least one half of the array is still sorted. So in each step I check which half is sorted by comparing the midpoint value with the left boundary; if the target falls within the sorted half's range, I narrow the search there, otherwise I search the other half. This keeps the O(log n) time complexity of binary search with O(1) extra space. Edge cases to mention in an interview: duplicates can degrade it to O(n) in the worst case, and I should clarify whether the array has duplicates before coding.

**中文要点：**
- 经典变体二分查找：旋转数组中任取中点，左右至少一半仍有序
- 每步判断哪一半有序（比较中点值与左边界），target 若落在有序半区间内就往该半收窄，否则搜另一半
- 时间 O(log n)，空间 O(1)
- 面试要提的边界：有重复元素时最坏退化到 O(n)，动手前先确认数组是否有重复

## 2. 你的 Harness 是怎么建的
**English:**
The harness is essentially the runtime environment around the model. I built it in three layers: an event loop that takes the model's output and dispatches it to tools or the user; a tool layer with a unified interface — every tool takes JSON in and returns a structured result, with timeouts and retries; and a state layer that manages the conversation history, with summarization and compaction so long sessions don't blow up the context window. On top of that there's a policy layer that decides things like when to stop, how to handle errors, and how to do permission checks for sensitive actions.
**中文要点：**
- Harness 定义：模型之外的运行时环境
- 三层结构：事件循环（event loop）→ 工具层（统一 JSON 接口、超时重试）→ 状态层（历史管理、summarization/compaction 防爆 context）
- 再加一层策略层（policy layer）：何时停止、错误处理、敏感操作的权限检查
- 强调"统一接口"是扩展性的关键

## 3. 在 Agent 整体架构设计里面，你认为最核心的模块是什么？
**English:**
I'd say the most critical piece is the control loop — the part that decides what to do next. The model itself is just a reasoning engine; without a good loop around it, you get an agent that either spins forever or gives up too early. A solid loop needs three things: good state management so it knows where it is in the task, a reliable tool-use contract so actions are actually executable, and a clear termination policy so it knows when to stop. Get those right, and even a mediocre model can do useful work; get them wrong, and the best model in the world will still flail.
**中文要点：**
- 核心答案：控制循环（control loop）——决定下一步做什么的模块
- 理由：模型只是推理引擎，循环决定成败
- 好循环的三要素：状态管理（知道任务进度）、可靠的工具契约（tool-use contract，动作可执行）、明确的终止策略
- 观点句：循环设计对了，中等模型也能干活；设计错了，最强模型也白搭

## 4. 本地 Agent 为什么会出现空转？
**English:**
Idling usually happens when the agent keeps looping without making real progress. The most common cause is the model generating "thinking" or placeholder actions instead of actual tool calls — for example, it says it'll check something but never actually calls the tool. Another big one is the loop waiting on a condition that will never be satisfied, like polling a task status that already failed silently. And sometimes it's simpler than that: the agent is just blocked waiting for user input or a long-running tool that never returns, and there's no timeout to break it out of the wait.
**中文要点：**
- 空转定义：循环继续但无实质进展
- 三个常见原因：模型只"思考"/占位不调工具；等待一个永远满足不了的条件（如静默失败的任务轮询）；阻塞等待用户输入或无返回的长任务，且无超时机制
- 回答结构：现象 → 三层原因递进（模型行为 → 逻辑缺陷 → 缺超时）

## 5. 你是怎么解决 Agent 空转问题的？
**English:**
I tackled it with a combination of detection and guardrails. First, I added a progress tracker: if the agent makes N consecutive steps without changing the task state or producing a new tool call, the loop flags it as idle. Then I added hard limits — a max step count and a per-step timeout — so nothing can spin forever. For the "thinking without acting" case, I added a nudge in the system prompt that pushes the model to prefer tool calls over narration, plus a fallback that asks the user for clarification when the agent is stuck. Since these changes, idle incidents in our logs dropped to nearly zero.
**中文要点：**
- 思路：检测（detection）+ 护栏（guardrails）两手
- 检测：连续 N 步无状态变化/无新工具调用 → 标记为空闲
- 护栏：最大步数限制 + 单步超时，物理上杜绝无限循环
- 针对"只想不做"：system prompt 引导优先调工具，卡住时回退到向用户澄清
- 结果量化：日志中空转事件降到接近零

## 6. 你有哪些 Agent 评测经验？
**English:**
I've built evals at two levels. At the unit level, I test individual components — like whether the tool parser correctly handles malformed inputs, or whether the summarizer preserves key facts. At the end-to-end level, I maintain a task-based eval set: real user requests with recorded reference trajectories and expected outcomes, and I score each run on task success, number of steps, and cost. I run these evals on every major change to the harness or prompts, so I can catch regressions before they ship. I've also done some human review sessions where we sample failed trajectories and categorize the failure modes to prioritize fixes.
**中文要点：**
- 两层评测：组件级（unit level，工具解析器、摘要器等）+ 端到端（end-to-end，真实任务集）
- 端到端评分维度：任务成功率、步数、成本
- 流程：每次大改动（harness/prompt）都跑评测防回归（regression）
- 人工环节：抽样失败轨迹，归类失败模式，指导修复优先级

## 7. 评测是人工评估还是机器评估？
**English:**
It's a mix, and they serve different purposes. Automated evals run on every change — they're fast and catch regressions, but they're mostly checking structured things like whether the final answer matches or whether the right tools were called. Human eval is slower and more expensive, so I reserve it for things machines can't judge well: the quality of a summary, whether the agent's tone was appropriate, or whether a "successful" run actually took a reasonable path. In practice, the automated suite is the daily driver, and human review happens weekly on sampled failures to keep the automated checks honest.
**中文要点：**
- 答案：两者结合，各司其职
- 机器评测：每次变更都跑，快速防回归，适合结构化检查（答案匹配、工具调用正确）
- 人工评测：慢而贵，用于机器判不好的维度（摘要质量、语气、路径合理性）
- 实际节奏：自动化是日常主力，人工每周抽样失败案例、校准自动化标准

## 8. 评测集和 Ground Truth 是如何构造的？
**English:**
I build the eval set from real production logs. I sample actual user requests, clean them up to remove personal data, and then have them labeled: for simple tasks, the ground truth is the expected final answer; for multi-step tasks, it's a reference trajectory plus the final state — for example, "file X was created with content Y." I also deliberately include edge cases and known failure scenarios so the set has good coverage. The set is versioned in git, and whenever we fix a bug in production, we add a regression case to the eval set so it never comes back.
**中文要点：**
- 来源：真实生产日志采样，脱敏后标注
- Ground truth 形式：简单任务是预期最终答案；多步任务是参考轨迹 + 最终状态（如"文件 X 被创建且内容为 Y"）
- 刻意加入边界情况和已知失败场景，保证覆盖度
- 维护：评测集用 git 版本管理，线上修 bug 就加回归用例，防止复发

## 9. 如何设计评价 Agent 系统好坏的指标体系？
**English:**
I'd design it in three tiers. The top tier is outcome metrics — task success rate and user satisfaction, because those are what actually matter. The middle tier is efficiency metrics — average steps per task, tokens and API cost per task, and latency. The bottom tier is quality and safety metrics — things like hallucination rate, unsafe action rate, and how often the agent asks for help when it's uncertain. Each metric needs a clear definition and a measurement method, and I'd weight them differently depending on the product stage: early on you optimize for success rate, later you push efficiency and cost down.
**中文要点：**
- 三层指标体系：结果层（任务成功率、用户满意度）→ 效率层（平均步数、token/成本、延迟）→ 质量安全层（幻觉率、不安全操作率、不确定时求助率）
- 每个指标要有明确定义和测量方法
- 权重随产品阶段调整：早期优先成功率，后期压效率和成本
- 体现"指标服务于阶段目标"的产品思维

## 10. 多用户同时调用 API，任务一多就卡死，怎么设计？
**English:**
This is fundamentally a concurrency and backpressure problem. First, I'd put requests into a queue with a bounded worker pool — so instead of every request spawning unlimited work, you cap concurrency and let the queue absorb spikes. Then add backpressure: when the queue gets too deep, return a "busy, try again" response or shed low-priority tasks instead of accepting everything and dying. For long tasks, make them async — return a task ID immediately and let the client poll or subscribe for results. And finally, isolate resources: rate-limit per user so one heavy user can't starve everyone else, and add timeouts plus circuit breakers on downstream calls so one slow dependency doesn't cascade.
**中文要点：**
- 定性：本质是并发控制 + 背压（backpressure）问题
- 有界工作池 + 请求队列：限制并发，队列吸收峰值
- 背压策略：队列过深时返回"繁忙请重试"或丢弃低优先级任务，而不是全盘接收后卡死
- 长任务异步化：立即返回 task ID，客户端轮询/订阅结果
- 资源隔离：按用户限流防"坏邻居"，下游调用加超时和熔断器防级联故障

## 11. 怎么沉淀部门级记忆 / 知识库？
**English:**
The core idea is to make knowledge capture a byproduct of the work itself rather than an extra chore. I think about three layers: first, a living documentation layer — structured docs for architecture decisions, runbooks, and postmortems, written right when decisions are made. Second, a process layer — templates and checklists embedded in onboarding, code review, and incident response so capturing knowledge happens inside the workflow, not after it. Third, a culture layer — things like tech-sharing sessions, rotating on-call shadowing, and rewarding people who write things down. The key metric is whether a new hire can solve a common problem without asking anyone, and if not, the knowledge base is incomplete.
**中文要点：**
- 让知识沉淀成为工作的副产品，而不是额外负担。
- 三层结构：文档层（架构决策、runbook、复盘记录）、流程层（onboarding/CR/事故响应模板）、文化层（分享会、影子值班）。
- 在决策发生时立刻记录，避免事后回忆失真。
- 用新人能否独立解决问题作为知识库完整性的检验标准。

## 12. 怎么解决"经验随人走"的问题？
**English:**
You can't fully eliminate it, but you can reduce the blast radius. First, identify the "bus factor" — which systems only one person understands — and treat that as a risk metric. Second, enforce redundancy through pair work, code reviews, and rotating on-call responsibilities, so at least two people always know any critical system. Third, require written artifacts: design docs, runbooks, and handover notes that a new person could actually act on, not just meeting notes. And finally, build a culture where sharing is rewarded — people leave anyway, so the goal is to make the team's capability bigger than any individual. The real fix is structural: knowledge should live in the system, not in someone's head.
**中文要点：**
- 无法完全消除，但能降低破坏半径（bus factor）。
- 识别关键单点人员，把 bus factor 当风险指标管理。
- 通过结对、CR、轮岗保证关键系统至少有两人懂。
- 要求可操作的书面产物：设计文档、runbook、交接笔记。
- 长期解是结构性的：知识住在系统里，而不是人脑里。

## 13. 介绍 Prompt Engineering、Context Engineering、Harness Engineering
**English:**
Prompt Engineering is about writing better instructions for the model — crafting clear, specific prompts with the right tone, format, and examples to get better outputs. Context Engineering goes one level up: it's about managing everything the model sees, not just the prompt — deciding what to retrieve from documents, what history to include, what tool results to inject, and how to budget the limited context window. Harness Engineering is about everything around the model: the agent scaffolding, orchestration, retries, evaluation, logging, and guardrails that make the raw model reliable in production. In practice, most production gains I've seen come from the harness layer, not from tweaking prompts.
**中文要点：**
- Prompt Engineering：写好指令，措辞、格式、示例引导输出。
- Context Engineering：管理模型看到的所有上下文——检索什么、塞什么历史、怎么分配有限的 context window。
- Harness Engineering：模型之外的工程脚手架——agent 编排、重试、评估、日志、护栏。
- 实战中大部分生产级收益来自 harness 层，而非微调 prompt。

## 18. Agent 的局限性
**English:**
Agents are powerful but have real limitations. First, reliability: they can fail in subtle ways — looping, hallucinating tool results, or silently making wrong assumptions — and these failures are hard to detect because the output looks confident. Second, context limits: they lose track of long-running tasks and struggle with very large codebases or state. Third, they lack real judgment: they can't tell when a task is ambiguous and should stop, or when "good enough" is actually good enough. Fourth, cost and latency: complex tasks burn a lot of tokens and take a long time, which doesn't scale. That's why in production we always need evaluation, guardrails, and human checkpoints for high-stakes actions.
**中文要点：**
- 可靠性：静默失败（循环、幻觉工具结果、错误假设）、输出过于自信。
- 上下文限制：长任务失忆、大代码库/大状态难处理。
- 缺乏判断力：不知道任务模糊时该停下、不知道何时"够好就行"。
- 成本与延迟：复杂任务烧 token、耗时长，难以规模化。
- 生产结论：必须配评估、护栏、高风险操作的人工确认。

## 19. 手撕：合并 K 个升序链表
**English:**
The cleanest approach is to use a min-heap. First, push the head of each non-empty list into the heap. Then repeatedly pop the smallest node, attach it to the result list, and push that node's next pointer into the heap if it exists. This gives O(N log K) time complexity, where N is the total number of nodes and K is the number of lists, and O(K) extra space for the heap. An alternative is divide and conquer — merge pairs of lists recursively — which is also O(N log K) but with less constant overhead. I'd go with the heap approach in an interview because it's straightforward to write correctly.
**中文要点：**
- 最小堆做法：把每条链表头节点入堆，反复取出最小节点、接到结果链、把它的 next 入堆。
- 时间复杂度 O(N log K)（N 总节点数，K 链表数），空间 O(K)。
- 备选方案：分治两两合并，同样 O(N log K)，常数更小。
- 堆做法更直观、面试时更不容易写错。
- 注意点：处理空链表、dummy head 简化拼接。
