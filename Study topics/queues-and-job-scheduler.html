Interview Prompt

Design a durable scheduler for research jobs.

Clarifying Questions

Must jobs survive restarts? What is the maximum run time? Can workers execute a task more than once?

Functional and Non-Functional Requirements

Support accepted/pending/running/succeeded/failed states and recover abandoned work. Assume at-least-once delivery, not exactly-once computation.

The numerical targets here are practice assumptions to negotiate with an interviewer, not measured project results.

Architecture and Data Flow

Design Decisions and Alternatives

Commit run and outbox together; dispatch asynchronously. Workers claim leases and publish results idempotently. Acknowledge only after durable state is saved.

A database queue can suffice at small scale; a broker improves decoupling but creates a dual-write problem unless an outbox bridges it.

Failure Scenarios

Worker dies after writing output but before ack: duplicate delivery must reuse or safely replace the same logical result.

Step-by-step interview script
  1. I would first clarify: Must jobs survive restarts? What is the maximum run time? Can workers execute a task more than once?
  2. I would propose this contract: Support accepted/pending/running/succeeded/failed states and recover abandoned work. Assume at-least-once delivery, not exactly-once computation.
  3. The main data flow is API → Transactional Run and Outbox → Dispatcher → Queue → Worker → Results.
  4. The key decision is: Commit run and outbox together; dispatch asynchronously. Workers claim leases and publish results idempotently. Acknowledge only after durable state is saved.
  5. The trade-off is: A database queue can suffice at small scale; a broker improves decoupling but creates a dual-write problem unless an outbox bridges it.
  6. I would test this failure: Worker dies after writing output but before ack: duplicate delivery must reuse or safely replace the same logical result.
  7. I would close by checking the design against the requirements and identifying the next measurement or implementation risk.

Follow-up Questions

Explain lease expiry, fencing and how you prevent two workers from committing conflicting results.

How would you adapt the design if traffic increased tenfold?

I would identify the saturated resource from measured utilization and queueing, then consider partitioning, caching or additional workers while preserving ownership, idempotency and data consistency. I would not assume that multiplying replicas fixes a serialized dependency.

Follow-up: Which component in your drawing is the first bottleneck?

Practice and Self-Review

First learning day: 15 minutes explanation, 20 minutes drawing, 10 minutes follow-ups. Paired practice day: 30 minutes independent design and spoken explanation, 15 minutes comparing requirements, data flow, failure handling and trade-offs with this case. On buffer days change one constraint.
