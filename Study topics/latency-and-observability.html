Topic

Latency and Observability

学习背景

这属于System Design：根据用户需求设计多个组件如何协作。先说明假设，再讨论容量、数据、失败和取舍。

Question

Diagnose a slow report service.

请设计 Latency and Observability 场景中的系统，说明需求、架构、取舍和失败处理。

Key Terms

Latency and Observability
用请求关联ID、日志、指标和追踪定位各环节耗时，观察p50和p95。
Requirement
系统必须满足的行为或性能约束。
Trade-off
一个选择带来的收益及付出的代价。
Failure mode
依赖或组件出错时的具体表现。

Interview Prompt

Diagnose a slow report service.

Clarifying Questions

Which user-visible operation is slow? What percentile and measurement window? Does it stream?

Functional and Non-Functional Requirements

Attribute queue wait, retrieval, model and tool time. Track failures alongside latency with a trace ID across components.

The numerical targets here are practice assumptions to negotiate with an interviewer, not measured project results.

Architecture and Data Flow

Design Decisions and Alternatives

Measure p50/p95 with sample counts and realistic concurrency. Optimize the measured bottleneck, then compare quality, cost and errors on the same workload.

Parallel independent calls reduce critical-path time but may raise cost and contention. Streaming improves perceived latency without necessarily reducing total completion time.

Failure Scenarios

Fast failed requests make average latency look better. Segment successful and failed requests and inspect saturation.

Step-by-step interview script
  1. I would first clarify: Which user-visible operation is slow? What percentile and measurement window? Does it stream?
  2. I would propose this contract: Attribute queue wait, retrieval, model and tool time. Track failures alongside latency with a trace ID across components.
  3. The main data flow is Client span → API span → Retrieval span → Tool span → Model span → Report span.
  4. The key decision is: Measure p50/p95 with sample counts and realistic concurrency. Optimize the measured bottleneck, then compare quality, cost and errors on the same workload.
  5. The trade-off is: Parallel independent calls reduce critical-path time but may raise cost and contention. Streaming improves perceived latency without necessarily reducing total completion time.
  6. I would test this failure: Fast failed requests make average latency look better. Segment successful and failed requests and inspect saturation.
  7. I would close by checking the design against the requirements and identifying the next measurement or implementation risk.

Follow-up Questions

Explain TTFT versus total latency and why percentiles cannot simply be added across stages.

How would you adapt the design if traffic increased tenfold?

I would identify the saturated resource from measured utilization and queueing, then consider partitioning, caching or additional workers while preserving ownership, idempotency and data consistency. I would not assume that multiplying replicas fixes a serialized dependency.

Follow-up: Which component in your drawing is the first bottleneck?

Practice and Self-Review

First learning day: 15 minutes explanation, 20 minutes drawing, 10 minutes follow-ups. Paired practice day: 30 minutes independent design and spoken explanation, 15 minutes comparing requirements, data flow, failure handling and trade-offs with this case. On buffer days change one constraint.
