学习背景

Question

Design safe retries for a job-submission service.

请设计 Retries, Idempotency and Consistency 场景中的系统，说明需求、架构、取舍和失败处理。

直观例子

把Risk Copilot当作具体系统：用户提交研究问题，系统检索或计算，再返回结果。围绕本页主题说明一个依赖变慢或失败后用户会看到什么。

Short Answer

Client → Idempotency Ledger → Transaction → Outbox → Worker → Result Commit Bind an idempotency key to a request hash. The same key with a different payload is a conflict. Retry safe operations with exponential backoff and jitter. Strong consistency helps admission invariants; eventually consistent progress displays may be acceptable. Do not promise exactly-once delivery from retry logic.

中文回答

Interview Prompt

Design safe retries for a job-submission service.

Clarifying Questions

Which operations have side effects? How long must deduplication records live? What does the caller see after an ambiguous timeout?

Functional and Non-Functional Requirements

Prevent duplicate logical effects and expose durable status. Retry transient failures within an overall deadline and bounded attempt budget.

The numerical targets here are practice assumptions to negotiate with an interviewer, not measured project results.

Architecture and Data Flow

Design Decisions and Alternatives

Bind an idempotency key to a request hash. The same key with a different payload is a conflict. Retry safe operations with exponential backoff and jitter.

Strong consistency helps admission invariants; eventually consistent progress displays may be acceptable. Do not promise exactly-once delivery from retry logic.

Failure Scenarios

Timeout after success: return the stored result on retry. Expired deduplication records can allow repetition; choose retention from business semantics.

Step-by-step interview script
  1. I would first clarify: Which operations have side effects? How long must deduplication records live? What does the caller see after an ambiguous timeout?
  2. I would propose this contract: Prevent duplicate logical effects and expose durable status. Retry transient failures within an overall deadline and bounded attempt budget.
  3. The main data flow is Client → Idempotency Ledger → Transaction → Outbox → Worker → Result Commit.
  4. The key decision is: Bind an idempotency key to a request hash. The same key with a different payload is a conflict. Retry safe operations with exponential backoff and jitter.
  5. The trade-off is: Strong consistency helps admission invariants; eventually consistent progress displays may be acceptable. Do not promise exactly-once delivery from retry logic.
  6. I would test this failure: Timeout after success: return the stored result on retry. Expired deduplication records can allow repetition; choose retention from business semantics.
  7. I would close by checking the design against the requirements and identifying the next measurement or implementation risk.

Follow-up Questions

Explain where to retry so layered retries do not multiply load.

How would you adapt the design if traffic increased tenfold?

I would identify the saturated resource from measured utilization and queueing, then consider partitioning, caching or additional workers while preserving ownership, idempotency and data consistency. I would not assume that multiplying replicas fixes a serialized dependency.

Follow-up: Which component in your drawing is the first bottleneck?

Practice and Self-Review
