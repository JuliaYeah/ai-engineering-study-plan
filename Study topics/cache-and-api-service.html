Question

Design caching for frequently requested financial reports.

请设计 Cache and API Service 场景中的系统，说明需求、架构、取舍和失败处理。

Short Answer

Client → Auth API → Versioned Cache → Report Service → Source data Key by authorization scope, normalized request and relevant versions. Use TTL for bounded staleness and single-flight protection for expensive misses. Read-through caching is simple; explicit invalidation is faster after changes but requires reliable event delivery. Interview Prompt

Design caching for frequently requested financial reports.

Clarifying Questions

How stale may a result be? Is access tenant-specific? Does the result depend on a model or data version?

Functional and Non-Functional Requirements

Reduce repeated work while preserving authorization and a stated freshness bound. Assume 100 reads per second with a 90 percent repeat ratio.

The numerical targets here are practice assumptions to negotiate with an interviewer, not measured project results.

Architecture and Data Flow

Design Decisions and Alternatives

Key by authorization scope, normalized request and relevant versions. Use TTL for bounded staleness and single-flight protection for expensive misses.

Read-through caching is simple; explicit invalidation is faster after changes but requires reliable event delivery. A cached answer still needs authorization.

Failure Scenarios

Stampede on expiration: coalesce work and jitter expiry. On cache failure, limit fallback concurrency instead of overwhelming the source.

Step-by-step interview script
  1. I would first clarify: How stale may a result be? Is access tenant-specific? Does the result depend on a model or data version?
  2. I would propose this contract: Reduce repeated work while preserving authorization and a stated freshness bound. Assume 100 reads per second with a 90 percent repeat ratio.
  3. The main data flow is Client → Auth API → Versioned Cache → Report Service → Source data.
  4. The key decision is: Key by authorization scope, normalized request and relevant versions. Use TTL for bounded staleness and single-flight protection for expensive misses.
  5. The trade-off is: Read-through caching is simple; explicit invalidation is faster after changes but requires reliable event delivery. A cached answer still needs authorization.
  6. I would test this failure: Stampede on expiration: coalesce work and jitter expiry. On cache failure, limit fallback concurrency instead of overwhelming the source.
  7. I would close by checking the design against the requirements and identifying the next measurement or implementation risk.

Follow-up Questions

Estimate hit-rate effect on backend load; explain why a semantic cache needs a correctness evaluation.

How would you adapt the design if traffic increased tenfold?

I would identify the saturated resource from measured utilization and queueing, then consider partitioning, caching or additional workers while preserving ownership, idempotency and data consistency. I would not assume that multiplying replicas fixes a serialized dependency.

Follow-up: Which component in your drawing is the first bottleneck?

Practice and Self-Review

First learning day: 15 minutes explanation, 20 minutes drawing, 10 minutes follow-ups. Paired practice day: 30 minutes independent design and spoken explanation, 15 minutes comparing requirements, data flow, failure handling and trade-offs with this case. On buffer days change one constraint.
