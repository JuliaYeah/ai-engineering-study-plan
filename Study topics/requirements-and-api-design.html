Requirements and API Design

学习背景

这属于System Design：根据用户需求设计多个组件如何协作。先说明假设，再讨论容量、数据、失败和取舍。

Question

Design an API for submitting financial risk calculations.

请设计 Requirements and API Design 场景中的系统，说明需求、架构、取舍和失败处理。

Interview Prompt

Design an API for submitting financial risk calculations.

Clarifying Questions

Who submits a calculation? Is completion synchronous? What makes two submissions the same logical request?

Functional and Non-Functional Requirements

Accept validated requests, return a run ID, expose status and results. Assume 10 submissions per second and a 2-second admission deadline; calculation completion has a separate objective.

The numerical targets here are practice assumptions to negotiate with an interviewer, not measured project results.

Architecture and Data Flow

Design Decisions and Alternatives

Use POST /runs with an idempotency key and GET /runs/{id}. Persist configuration and ownership before acknowledging acceptance. Keep expensive calculation out of the request path.

Synchronous execution is simpler for consistently short jobs. A queue adds operational cost but isolates slow calculations and allows recovery.

Failure Scenarios

Client times out after acceptance: retrying with the same key returns the same run. Unknown ownership must not leak result existence.

Step-by-step interview script
  1. I would first clarify: Who submits a calculation? Is completion synchronous? What makes two submissions the same logical request?
  2. I would propose this contract: Accept validated requests, return a run ID, expose status and results. Assume 10 submissions per second and a 2-second admission deadline; calculation completion has a separate objective.
  3. The main data flow is Client → API validation → Run database → Worker → Result store → Status API.
  4. The key decision is: Use POST /runs with an idempotency key and GET /runs/{id}. Persist configuration and ownership before acknowledging acceptance. Keep expensive calculation out of the request path.
  5. The trade-off is: Synchronous execution is simpler for consistently short jobs. A queue adds operational cost but isolates slow calculations and allows recovery.
  6. I would test this failure: Client times out after acceptance: retrying with the same key returns the same run. Unknown ownership must not leak result existence.
  7. I would close by checking the design against the requirements and identifying the next measurement or implementation risk.

Follow-up Questions

Estimate daily runs and retention storage; separate admission latency from completion latency.

How would you adapt the design if traffic increased tenfold?

I would identify the saturated resource from measured utilization and queueing, then consider partitioning, caching or additional workers while preserving ownership, idempotency and data consistency. I would not assume that multiplying replicas fixes a serialized dependency.

Follow-up: Which component in your drawing is the first bottleneck?

Practice and Self-Review

First learning day: 15 minutes explanation, 20 minutes drawing, 10 minutes follow-ups. Paired practice day: 30 minutes independent design and spoken explanation, 15 minutes comparing requirements, data flow, failure handling and trade-offs with this case. On buffer days change one constraint.
