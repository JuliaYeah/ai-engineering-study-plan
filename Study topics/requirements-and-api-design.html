Question

Design an API for submitting financial risk calculations.

Key Terms

  • Requirements and API Design：先确认用户、负载和业务约束，再定义资源、状态与API契约。
  • Requirement：系统必须满足的行为或性能约束。
  • Trade-off：一个选择带来的收益及付出的代价。
  • Failure mode：依赖或组件出错时的具体表现。

Short Answer

Client → API validation → Run database → Worker → Result store → Status API Use POST /runs with an idempotency key and GET /runs/{id}. Persist configuration and ownership before acknowledging acceptance. Keep expensive calculation out of the request path. Synchronous execution is simpler for consistently short jobs. A queue adds operational cost but isolates slow calculations and allows recovery.

中文回答

先确认用户、负载和业务约束，再定义资源、状态与API契约。耗时研究任务返回任务ID，由用户查询状态；说明认证、错误和幂等规则。

参考答案

每一题先遮住答案，自己用英文说一遍，再点开对照。英文答法是可以直接在面试里说的版本，不需要逐字背，记住要点和顺序就行。

1. Who submits a calculation?
谁来提交计算？

为什么要问：调用方决定了认证方式、权限和限流。面试官一般不会主动告诉你，先问清楚再设计。

合理的假设：

  • 内部风险分析师通过网页提交
  • 内部系统用服务账号提交，比如每天收盘后的批量任务
  • 每个run都记录owner（用户或团队），只有owner能看状态和结果
  • 限流按用户和按服务账号分别算

英文答法

I'd assume two kinds of callers: risk analysts using an internal web UI, and internal services, such as an end-of-day batch job, using service accounts. Every request is authenticated, and every run records an owner, so only that owner or their team can read its status and results. Knowing the callers also tells me how to rate-limit: per user and per service account.

2. Is completion synchronous?
计算结果是同步返回吗？

为什么要问：计算要跑多久，决定API是同步还是异步。

风险计算（比如蒙特卡洛VaR、压力测试）可能要几秒到几十分钟，远远超过一个HTTP请求能等的时间（网关和浏览器通常30到60秒就超时）。所以设计成异步：

  • 2秒内接受请求，返回 202 Accepted 和 run_id
  • 客户端之后查状态（轮询），或者完成时收到通知
  • 只有当计算总是在1秒左右完成时，同步才更简单

英文答法

No. A risk calculation, for example a Monte Carlo VaR or a stress test, can take anywhere from seconds to tens of minutes, which is far longer than an HTTP request should stay open. So I'd make the API asynchronous: it accepts the request within two seconds and returns 202 Accepted with a run ID, and the client polls a status endpoint or gets notified when the run finishes. If every calculation reliably finished in under a second, a synchronous API would be simpler, and I'd choose that.

3. What makes two submissions the same logical request?
什么情况下，两次提交算同一个请求？

这是幂等性（idempotency）问题。网络超时后客户端会重试；如果服务器把重试当成新请求，就会算两次。

做法：

  • 客户端为每一次“逻辑上的提交”生成一个 Idempotency-Key（一个UUID），重试时带同一个key
  • 服务器在 (owner_id, idempotency_key) 上建唯一索引
  • key相同、内容也相同：返回原来那个run
  • key相同、内容不同：返回 409 Conflict，这是客户端的bug

不要只按“内容相同”来判断：两个分析师可以合法地提交同样的参数，一个人也可能故意重跑。

英文答法

Two submissions are the same logical request when they carry the same idempotency key from the same caller. The client generates a UUID for each logical submission and reuses it on every retry. The server stores the key with a unique constraint on owner and key. Same key and same body: return the original run. Same key but a different body: return 409 Conflict, because that's a client bug. I wouldn't deduplicate on the payload alone, because two analysts can legitimately submit identical inputs, and someone may want to re-run a calculation on purpose.

4. What are the functional and non-functional requirements?
功能需求和非功能需求怎么说？

功能需求（系统要做什么）：

  • 提交一次计算：portfolio、计算类型（VaR、压力测试）、参数、as-of日期
  • 查状态：queued / running / succeeded / failed / cancelled
  • 取结果、列出我的runs，可选：取消一个run

非功能需求（做得多好）：

  • 峰值每秒10次提交；接受请求（admission）p99小于2秒
  • 计算完成时间单独定目标，比如95%的run在10分钟内完成
  • 可靠：返回run_id之后，这个run不会丢，也不会被算两次
  • 安全：认证和owner检查，结果不会泄露给别人
  • 可审计：保存输入、模型版本和市场数据快照，结果可以复现（金融监管要求）

英文答法

Functionally, a user can submit a calculation, check its status, fetch the results, list their runs, and optionally cancel one. Non-functionally, peak load is about 10 submissions per second, and accepting a request should take under 2 seconds at p99. Completion has its own target, say 95% of runs finish within 10 minutes. Once we return a run ID, the run must never be lost or executed twice. And because this is finance, every run should be reproducible, so we store its inputs, the model version and the market-data snapshot it used.

5. What does the API look like?
API具体长什么样？

资源是run（一次计算）。用名词加HTTP方法；创建时返回 202 Accepted 而不是 201 Created，表示“已经接受，但还没做完”。

POST /v1/runs
Authorization: Bearer <token>
Idempotency-Key: 3f6c2a9e-8d41-4b7a-9e0f-2c5d7a1b9e63

{
  "portfolio_id": "pf_123",
  "calc_type": "var",
  "params": { "confidence": 0.99, "horizon_days": 10, "method": "historical" },
  "as_of": "2026-11-06"
}

-> 202 Accepted
   Location: /v1/runs/run_8a7b
   { "run_id": "run_8a7b", "status": "queued" }

GET /v1/runs/run_8a7b
-> 200 { "run_id": "run_8a7b", "status": "running",
         "submitted_at": "...", "started_at": "...", "finished_at": null, "error": null }

GET  /v1/runs/run_8a7b/result     -> 200 结果；还没完成 -> 409；结果很大时分页或给下载链接
GET  /v1/runs?status=failed&cursor=...   -> 我的runs，按cursor分页
POST /v1/runs/run_8a7b/cancel     -> 202

状态机：queued → running → succeeded / failed / cancelled。

错误码：

  • 400 输入不合法，指出是哪个字段
  • 401 没有登录
  • 404 run不存在，或者不是你的（两种情况返回一样，见第8题）
  • 409 同一个key但内容不同，或者结果还没准备好
  • 429 超过限流，带 Retry-After 告诉客户端多久后再试

英文答法

The resource is a run. POST /v1/runs creates one and returns 202 Accepted with the run ID, because the work hasn't happened yet. GET /v1/runs/{id} returns the status, which moves from queued to running, and then to succeeded, failed or cancelled. GET /v1/runs/{id}/result returns the output once the run has succeeded. Errors are explicit: 400 with field-level messages for invalid input, 404 for a run that doesn't exist or isn't yours, 409 for a reused idempotency key with a different body, and 429 with Retry-After when a client exceeds its rate limit.

6. Walk me through the data flow. Why persist before acknowledging?
请求进来以后发生了什么？为什么要先存数据库再返回？

一个请求的完整路径：

  1. API认证，校验输入：格式对不对，portfolio存不存在，调用者有没有权限
  2. 在一个数据库事务里写入runs表一行，status = queued。(owner_id, idempotency_key) 有唯一索引；冲突说明是重试，按第3题的规则返回已有的run
  3. 把 {run_id} 放进队列（比如SQS）
  4. 返回 202 和run_id。重的计算从不在请求里做，所以接受请求能稳定在2秒以内
  5. Worker从队列取消息，先“认领”这个run：UPDATE runs SET status = 'running' WHERE run_id = ? AND status = 'queued'，只有一个worker能更新成功
  6. Worker读取portfolio和市场数据，计算；结果按run_id写进对象存储（S3），再把status改成succeeded并记下结果位置
  7. 状态API只读runs表

runs表：run_id（主键）、owner_id、idempotency_key、request_hash、calc_type、params、portfolio_id、as_of、model_version、status、attempts、created_at、started_at、finished_at、error、result_location。

为什么先存再返回：如果先返回run_id、后写数据库，中间服务器崩溃，用户手里就有一个根本不存在的run_id，“已接受”的承诺就丢了。

一个容易漏的缺口：数据库写成功了，但放进队列失败。两种解决办法：

  • transactional outbox：同一个事务里多写一条outbox记录，后台进程负责把它投递到队列
  • 定时扫描：status还是queued、超过N分钟的run，重新放进队列

队列一般是至少投递一次（at-least-once），同一条消息可能来两次，所以worker要用第5步的条件更新来认领，认领失败就丢掉这条消息。

英文答法

The API authenticates the caller and validates the input. Then, in one transaction, it inserts a run row with status queued, with a unique constraint on owner and idempotency key, so a retry finds the existing row. It puts the run ID on a queue and returns 202 with the run ID. A worker picks up the message, claims the run with a conditional update from queued to running, so only one worker wins, computes the result, writes it to object storage keyed by run ID, and marks the run succeeded. I persist before acknowledging because once I've handed out a run ID, a crash must not lose that run. And since the database write and the enqueue can't be one atomic step, I'd use a transactional outbox or a sweeper that re-enqueues runs stuck in queued.

7. What are the trade-offs: synchronous vs. asynchronous, polling vs. callbacks?
有哪些取舍？同步还是异步？轮询还是回调？

同步：

  • 好处：一个请求搞定，不需要队列和状态表，最简单
  • 代价：慢的计算会占住API的连接和线程，超时就白算；API重启会丢掉正在算的任务
  • 适合：计算总是很短（1秒左右）

异步（队列 + worker）：

  • 好处：慢的计算和API隔离；重启不丢任务；可以重试；worker可以单独扩容
  • 代价：多了队列、状态表和更多需要运维的组件；客户端要查状态

怎么知道算完了：

  • 轮询（polling）：最简单，适合网页；服务器用 Retry-After 建议隔多久查一次
  • 回调（webhook）：适合其他服务调用，不用一直查；但要处理回调失败和重试
  • 我会先做轮询，有服务类调用方时再加webhook

英文答法

Synchronous execution is simpler: one request, no queue, no status table. But slow calculations would hold API connections, a client timeout wastes the work, and a restart loses in-flight jobs, so it only fits consistently short jobs. A queue with workers costs more to operate, but it isolates slow calculations from the API, survives restarts, allows retries, and lets me scale workers independently of the API. For completion, I'd start with polling, using Retry-After to suggest an interval, and add webhooks later for service clients, since webhooks need their own retry handling.

8. What can fail, and what happens then?
哪里会出错？出错时会怎样？
  • 服务器已经接受了，但客户端超时没收到回复：客户端用同一个Idempotency-Key重试，拿到同一个run_id，不会重复计算
  • 同一个key、不同内容：返回 409
  • Worker算到一半崩溃：认领时设一个租约（lease_until），租约过期后别的worker重新认领，attempts加1；失败3次标记为failed，消息进死信队列（DLQ）等人查。所以计算必须可以安全重跑：结果按run_id写，覆盖也没关系
  • 队列不可用：数据库里已经有这行，outbox或定时扫描之后会补投递；API照常接受请求
  • 有人查别人的run：返回 404，和run不存在时一模一样，不返回 403。返回403等于告诉对方“这个run存在，只是你没权限”。页面上 “Unknown ownership must not leak result existence” 说的就是这个
  • 提交突然暴增：队列先接住；超过每个调用方的限额返回 429；按队列积压自动增加worker

英文答法

If the client times out after we accepted, it retries with the same idempotency key and gets the same run back, so nothing is computed twice. If a worker crashes mid-run, its lease expires and another worker re-claims the run; after three attempts the run is marked failed and the message goes to a dead-letter queue. That's why the calculation must be safe to re-run, and results are written by run ID. If someone asks for a run that isn't theirs, they get 404, exactly like a run that doesn't exist, because a 403 would reveal that the run exists. And a burst of submissions is absorbed by the queue, with per-client rate limits returning 429.

9. Follow-up: Estimate daily runs and retention storage; separate admission latency from completion latency.
追问：估算每天有多少个run、要存多少数据；把“接受请求的延迟”和“计算完成的延迟”分开说。

每天多少个run：

  • 每秒10次是峰值。假设全天平均是峰值的十分之一，也就是每秒1次
  • 1 × 86,400秒 ≈ 每天约10万个run（取整，方便算）

存多少数据：

  • 元数据：每行约2 KB，10万 × 2 KB = 每天200 MB，一年约73 GB，一台Postgres足够
  • 结果：假设每个50 KB（每个持仓的风险值加汇总），每天5 GB，一年约1.8 TB
  • 金融数据常要保存7年：结果约13 TB，放S3，90天后自动转到更便宜的存储层；数据库只存结果的位置

两种延迟要分开：

  • 接受请求的延迟（admission latency）：从POST到拿到202。只有校验、一次写库、一次入队，通常几十到几百毫秒，目标p99小于2秒，在API层测
  • 计算完成的延迟（completion latency）：从submitted_at到finished_at，等于排队时间加计算时间，取决于worker够不够

需要多少worker（Little's Law：同时在跑的数量 = 到达速率 × 平均耗时）：

  • 平均每秒1个 × 每个算60秒 = 平均60个同时在跑
  • 峰值每秒10个时需要600个，否则队列变长、完成时间变长。所以按队列积压自动扩容，或者接受高峰时完成得慢一些

英文答法

Ten per second is the peak. If the average is a tenth of that, it's about one per second, so roughly 100,000 runs a day. At about 2 KB of metadata per run, that's 200 MB a day, around 73 GB a year, which fits in one Postgres instance. If each result is about 50 KB, that's 5 GB a day, about 1.8 TB a year, and around 13 TB over a seven-year retention period, so results go to object storage with lifecycle rules, and the database keeps only their location. Admission latency is just validation, one write and one enqueue, so it should be well under the two-second target. Completion latency is queue wait plus compute time, and it depends on worker capacity: by Little's Law, one run per second at sixty seconds each means about sixty runs in flight on average, and the peak needs far more, so I'd autoscale workers on queue age.

10. Follow-up: How would you adapt the design if traffic increased tenfold?
追问：流量变成10倍，设计要怎么改？

变成峰值每秒100次提交。先测量哪里饱和，不要默认“多加几台机器”就能解决。

  • 接受请求这条路：API是无状态的，加实例就行；每秒100次写入对Postgres不算多；SQS也没问题
  • 计算是10倍：按队列积压自动扩容worker，成本也接近10倍。减少计算量的办法：
    • 同一个as-of日期的市场数据只加载一次，多个run共用
    • 输入完全相同的计算复用结果（按输入内容的哈希查，这和幂等key是两回事）
    • 分开交互队列和批量队列，分析师不用排在夜间批量任务后面
  • 查状态的读请求也是10倍：读副本或缓存；用推送代替频繁轮询
  • 公平：按调用方设配额，一个批量任务不能把所有worker占满
  • 共享依赖：如果市场数据服务只有一个实例，加worker只会把它压垮，要先给它扩容或加缓存

英文答法

At a hundred submissions per second, the admission path is still easy: the API is stateless, so I add replicas, and a hundred inserts per second is modest for Postgres. The real cost is compute, which grows tenfold. I'd autoscale workers on queue age, and reduce the work itself: load each day's market data once and share it, reuse results for identical inputs by content hash, and split interactive and batch queues so analysts don't wait behind a nightly batch. I'd add per-client quotas for fairness, and move status reads to a replica or push notifications. Above all, I'd measure where saturation actually is, because adding workers doesn't help if they all depend on one market-data service.

11. Follow-up: Which component in your drawing is the first bottleneck?
追问：你画的图里，哪个组件最先成为瓶颈？

Worker（计算能力），以及worker依赖的服务（市场数据、portfolio服务）。

  • 提交这条路很轻：校验、写一行、入队
  • 队列会先把突增的请求接住，所以第一个症状不是提交失败，而是队列积压时间和完成时间变长，接受请求的延迟仍然很快
  • 这正是要把两种延迟分开测的原因：只看API延迟会以为一切正常

第二个候选：runs数据库。如果几千个客户端每秒都在轮询，读请求会压过写入。办法：用Retry-After让客户端查得慢一点、读副本或缓存、webhook。

英文答法

The workers, and the services they depend on, such as market data. The submission path is light, and the queue absorbs bursts, so the first symptom isn't failed submissions but growing queue age and completion latency, while admission latency still looks healthy. That's exactly why I measure the two separately. The second candidate is the runs database under heavy polling, which I'd handle with Retry-After hints, a read replica or cache, and webhooks.

5分钟英文口述稿（把上面串起来说一遍）

英文答法

Before designing, I'd ask three questions: who submits calculations, whether completion has to be synchronous, and what makes two submissions the same request. I'll assume analysts and internal services, calculations that take seconds to tens of minutes, and a client-generated idempotency key.

英文答法

So the requirements are: submit a run, check its status, and fetch results; about 10 submissions per second at peak; accept within 2 seconds; completion has its own target; and an accepted run is never lost or run twice.

英文答法

The API has two main endpoints. POST /v1/runs takes the portfolio, calculation type, parameters and an Idempotency-Key header, and returns 202 Accepted with a run ID. GET /v1/runs/{id} returns the status: queued, running, succeeded or failed, plus a result link once it's done.

英文答法

For the data flow: the API validates the request and writes the run to the database with a unique constraint on owner and idempotency key, and only then returns the run ID. It puts the run on a queue; a worker claims it with a conditional update, computes, writes the result to object storage, and marks it succeeded. The expensive work never sits in the request path.

英文答法

The main trade-off is asynchronous versus synchronous. A queue adds moving parts, but it isolates slow calculations, survives restarts and lets workers scale independently.

英文答法

For failures: if the client times out and retries with the same key, it gets the same run. If a worker crashes, its lease expires and another worker picks the run up. And a run that isn't yours returns 404, so we never reveal that it exists.

英文答法

Finally, I'd check this against the requirements, and point out that the first bottleneck will be worker capacity, so I'd monitor queue age and completion latency separately from admission latency.

英文深入材料、实验与参考代码

Interview Prompt

Design an API for submitting financial risk calculations.

Clarifying Questions

Who submits a calculation? Is completion synchronous? What makes two submissions the same logical request?

Functional and Non-Functional Requirements

Accept validated requests, return a run ID, expose status and results. Assume 10 submissions per second and a 2-second admission deadline; calculation completion has a separate objective.

The numerical targets here are practice assumptions to negotiate with an interviewer, not measured project results.

Architecture and Data Flow

Design Decisions and Alternatives

Use POST /runs with an idempotency key and GET /runs/{id}. Persist configuration and ownership before acknowledging acceptance. Keep expensive calculation out of the request path.

Synchronous execution is simpler for consistently short jobs. A queue adds operational cost but isolates slow calculations and allows recovery.

Failure Scenarios

Client times out after acceptance: retrying with the same key returns the same run. Unknown ownership must not leak result existence.

Step-by-step interview script
  1. I would first clarify: Who submits a calculation? Is completion synchronous? What makes two submissions the same logical request?
  2. I would propose this contract: Accept validated requests, return a run ID, expose status and results. Assume 10 submissions per second and a 2-second admission deadline; calculation completion has a separate objective.
  3. The main data flow is Client → API validation → Run database → Worker → Result store → Status API.
  4. The key decision is: Use POST /runs with an idempotency key and GET /runs/{id}. Persist configuration and ownership before acknowledging acceptance. Keep expensive calculation out of the request path.
  5. The trade-off is: Synchronous execution is simpler for consistently short jobs. A queue adds operational cost but isolates slow calculations and allows recovery.
  6. I would test this failure: Client times out after acceptance: retrying with the same key returns the same run. Unknown ownership must not leak result existence.
  7. I would close by checking the design against the requirements and identifying the next measurement or implementation risk.

Follow-up Questions

Estimate daily runs and retention storage; separate admission latency from completion latency.

How would you adapt the design if traffic increased tenfold?

I would identify the saturated resource from measured utilization and queueing, then consider partitioning, caching or additional workers while preserving ownership, idempotency and data consistency. I would not assume that multiplying replicas fixes a serialized dependency.
