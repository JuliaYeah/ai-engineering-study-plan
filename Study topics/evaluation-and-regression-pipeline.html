Design an evaluation gate for an AI release.

Interview Prompt

Design an evaluation gate for an AI release.

Clarifying Questions

Which failures block a release? Are labels reliable? What is the budget for real model calls?

Functional and Non-Functional Requirements

Run deterministic tests on each PR, small model-dependent evaluations on controlled releases, and retain comparable records.

The numerical targets here are practice assumptions to negotiate with an interviewer, not measured project results.

Architecture and Data Flow

Design Decisions and Alternatives

Track task success, severe failures, latency and cost. Segment by scenario and inspect disagreements. Use deterministic assertions for numbers and calibrated human/LLM review for open text.

A single composite score simplifies a dashboard but can hide safety or correctness regressions. Keep hard constraints distinct from optimization metrics.

Failure Scenarios

The team tunes repeatedly on the held-out set: create a new independent evaluation before claiming generalization.

AI Decision Checklist

  • Model: start with a measured task baseline; select by quality, latency, cost and permitted data handling.
  • Data and context: preserve source/version/permission scope; validate generated tool arguments outside the model.
  • Evaluation: use representative development and held-out cases, deterministic checks for numbers, human-calibrated review for open text.
  • Failures and oversight: bound calls and spend, distinguish failure from success, require real authorization for consequential actions.
  • Cost and latency: record tokens, retries, queue wait and critical-path stages; re-evaluate quality after optimization.
Step-by-step interview script
  1. I would first clarify: Which failures block a release? Are labels reliable? What is the budget for real model calls?
  2. I would propose this contract: Run deterministic tests on each PR, small model-dependent evaluations on controlled releases, and retain comparable records.
  3. The main data flow is Versioned Dataset → Candidate Build → Offline Tests → Model Evals → Human Review → Release Gate.
  4. The key decision is: Track task success, severe failures, latency and cost. Segment by scenario and inspect disagreements. Use deterministic assertions for numbers and calibrated human/LLM review for open text.
  5. The trade-off is: A single composite score simplifies a dashboard but can hide safety or correctness regressions. Keep hard constraints distinct from optimization metrics.
  6. I would test this failure: The team tunes repeatedly on the held-out set: create a new independent evaluation before claiming generalization.
  7. I would close by checking the design against the requirements and identifying the next measurement or implementation risk.

Follow-up Questions

How do you manage flaky model outputs and confidence with a small dataset?

How would you adapt the design if traffic increased tenfold?

I would identify the saturated resource from measured utilization and queueing, then consider partitioning, caching or additional workers while preserving ownership, idempotency and data consistency. I would not assume that multiplying replicas fixes a serialized dependency.

Follow-up: Which component in your drawing is the first bottleneck?
