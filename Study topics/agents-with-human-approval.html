学习背景

Question

Design a tool-using agent that requires approval before a consequential action.

请设计 Agents with Human Approval 场景中的系统，说明需求、架构、取舍和失败处理。

Interview Prompt

Design a tool-using agent that requires approval before a consequential action.

Clarifying Questions

Which actions require approval? Who may approve? What if state changes between approval and execution?

Functional and Non-Functional Requirements

Plan bounded tool calls, pause on approval, persist state and record the approved action payload.

The numerical targets here are practice assumptions to negotiate with an interviewer, not measured project results.

Architecture and Data Flow

Design Decisions and Alternatives

Use deterministic workflow edges where possible. Bind approval to action parameters and state/version; reject changed or expired approvals. Limit iterations and tool permissions.

An autonomous loop is flexible but harder to test. A fixed workflow with a small planning step is easier to reason about for regulated calculations.

Failure Scenarios

Resume executes twice after a crash: side-effect tools need idempotency. Model-generated approval text is never a real human approval.

AI Decision Checklist

  • Model: start with a measured task baseline; select by quality, latency, cost and permitted data handling.
  • Data and context: preserve source/version/permission scope; validate generated tool arguments outside the model.
  • Evaluation: use representative development and held-out cases, deterministic checks for numbers, human-calibrated review for open text.
  • Failures and oversight: bound calls and spend, distinguish failure from success, require real authorization for consequential actions.
  • Cost and latency: record tokens, retries, queue wait and critical-path stages; re-evaluate quality after optimization.
Step-by-step interview script
  1. I would first clarify: Which actions require approval? Who may approve? What if state changes between approval and execution?
  2. I would propose this contract: Plan bounded tool calls, pause on approval, persist state and record the approved action payload.
  3. The main data flow is User → Planner → Tool Schema Validation → Approval Record → Authorized Executor → Audit Log.
  4. The key decision is: Use deterministic workflow edges where possible. Bind approval to action parameters and state/version; reject changed or expired approvals. Limit iterations and tool permissions.
  5. The trade-off is: An autonomous loop is flexible but harder to test. A fixed workflow with a small planning step is easier to reason about for regulated calculations.
  6. I would test this failure: Resume executes twice after a crash: side-effect tools need idempotency. Model-generated approval text is never a real human approval.
  7. I would close by checking the design against the requirements and identifying the next measurement or implementation risk.

Follow-up Questions

How are rejection, timeout, cancellation and resumed state represented?

How would you adapt the design if traffic increased tenfold?

I would identify the saturated resource from measured utilization and queueing, then consider partitioning, caching or additional workers while preserving ownership, idempotency and data consistency. I would not assume that multiplying replicas fixes a serialized dependency.

Follow-up: Which component in your drawing is the first bottleneck?

Practice and Self-Review

First learning day: 15 minutes explanation, 20 minutes drawing, 10 minutes follow-ups. Paired practice day: 30 minutes independent design and spoken explanation, 15 minutes comparing requirements, data flow, failure handling and trade-offs with this case. On buffer days change one constraint.
