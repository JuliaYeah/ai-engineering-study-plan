Interview Prompt

Design persistent experiment runs, predictions and metrics.

Clarifying Questions

What is the grain of a prediction? Can a run be retried? Which queries must be fast?

Functional and Non-Functional Requirements

Store one logical run per request key, multiple attempts per run and one prediction per model/data/as-of key. Assume recent status reads dominate historical scans.

The numerical targets here are practice assumptions to negotiate with an interviewer, not measured project results.

Architecture and Data Flow

Design Decisions and Alternatives

Use foreign keys and unique constraints. Index run ownership/status and prediction run/as-of access patterns. Store artifact URI and checksum separately from relational metadata.

A JSON payload helps evolving optional metadata; typed columns protect frequently queried invariants. Indexes increase write cost.

Failure Scenarios

A retry inserts duplicate predictions: a unique key prevents double publication. A migration needs backward-compatible readers during rollout.

Step-by-step interview script
  1. I would first clarify: What is the grain of a prediction? Can a run be retried? Which queries must be fast?
  2. I would propose this contract: Store one logical run per request key, multiple attempts per run and one prediction per model/data/as-of key. Assume recent status reads dominate historical scans.
  3. The main data flow is API → Runs and Attempts → Predictions and Metrics → Query API.
  4. The key decision is: Use foreign keys and unique constraints. Index run ownership/status and prediction run/as-of access patterns. Store artifact URI and checksum separately from relational metadata.
  5. The trade-off is: A JSON payload helps evolving optional metadata; typed columns protect frequently queried invariants. Indexes increase write cost.
  6. I would test this failure: A retry inserts duplicate predictions: a unique key prevents double publication. A migration needs backward-compatible readers during rollout.
  7. I would close by checking the design against the requirements and identifying the next measurement or implementation risk.

Follow-up Questions

Explain a composite index order and how you would confirm the query plan.

How would you adapt the design if traffic increased tenfold?

I would identify the saturated resource from measured utilization and queueing, then consider partitioning, caching or additional workers while preserving ownership, idempotency and data consistency. I would not assume that multiplying replicas fixes a serialized dependency.

Follow-up: Which component in your drawing is the first bottleneck?

Practice and Self-Review

First learning day: 15 minutes explanation, 20 minutes drawing, 10 minutes follow-ups. Paired practice day: 30 minutes independent design and spoken explanation, 15 minutes comparing requirements, data flow, failure handling and trade-offs with this case. On buffer days change one constraint.
