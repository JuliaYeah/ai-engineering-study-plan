学习背景

这属于System Design：根据用户需求设计多个组件如何协作。先说明假设，再讨论容量、数据、失败和取舍。

Question

Release a containerized AI API safely.

请设计 CI/CD and AWS Deployment 场景中的系统，说明需求、架构、取舍和失败处理。

Key Terms

CI/CD and AWS Deployment
自动验证代码后构建版本化镜像，使用最小权限部署并做健康检查。
Requirement
系统必须满足的行为或性能约束。
Trade-off
一个选择带来的收益及付出的代价。
Failure mode
依赖或组件出错时的具体表现。

Interview Prompt

Release a containerized AI API safely.

Clarifying Questions

What state must survive task replacement? What requires a secret? What gates a release and rollback?

Functional and Non-Functional Requirements

Build a versioned image, run deterministic checks, perform a controlled deployment and smoke test, retain the last known-good version.

The numerical targets here are practice assumptions to negotiate with an interviewer, not measured project results.

Architecture and Data Flow

Design Decisions and Alternatives

Separate PR tests from paid integration checks. Use short-lived federated credentials, least-privilege roles and explicit image digests. Configure health checks and rollback instructions.

A single task is a learning deployment, not high availability. Externalize durable state before relying on task replacement for recovery.

Failure Scenarios

A container passes health checks but returns bad answers: add a small behavioral smoke set and retain evaluation evidence.

Step-by-step interview script
  1. I would first clarify: What state must survive task replacement? What requires a secret? What gates a release and rollback?
  2. I would propose this contract: Build a versioned image, run deterministic checks, perform a controlled deployment and smoke test, retain the last known-good version.
  3. The main data flow is GitHub Actions → OIDC role → ECR image → ECS Fargate → CloudWatch.
  4. The key decision is: Separate PR tests from paid integration checks. Use short-lived federated credentials, least-privilege roles and explicit image digests. Configure health checks and rollback instructions.
  5. The trade-off is: A single task is a learning deployment, not high availability. Externalize durable state before relying on task replacement for recovery.
  6. I would test this failure: A container passes health checks but returns bad answers: add a small behavioral smoke set and retain evaluation evidence.
  7. I would close by checking the design against the requirements and identifying the next measurement or implementation risk.

Follow-up Questions

Explain database migration compatibility, secret handling and the exact rollback boundary.

How would you adapt the design if traffic increased tenfold?

I would identify the saturated resource from measured utilization and queueing, then consider partitioning, caching or additional workers while preserving ownership, idempotency and data consistency. I would not assume that multiplying replicas fixes a serialized dependency.

Follow-up: Which component in your drawing is the first bottleneck?

Practice and Self-Review

First learning day: 15 minutes explanation, 20 minutes drawing, 10 minutes follow-ups. Paired practice day: 30 minutes independent design and spoken explanation, 15 minutes comparing requirements, data flow, failure handling and trade-offs with this case. On buffer days change one constraint.
